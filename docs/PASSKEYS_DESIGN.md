# Persona Passkeys (WebAuthn) Design

> [English](PASSKEYS_DESIGN.md) | [中文](PASSKEYS_DESIGN.zh.md)

Status: Design draft (pending review) · Date: 2026-09-13 · Roadmap: Milestone 4 "1Password Parity"

## 1. Background and Goals

A passkey is a WebAuthn/FIDO2 discoverable credential: one ES256 key pair per relying party (RP, i.e. a website), with the private key never leaving the authenticator. 1Password and Bitwarden both implement themselves as **software authenticators**: the private key is encrypted inside the password vault, syncs with the vault, and a browser-side hook intercepts `navigator.credentials` to complete registration/assertion with the vault's private key.

Persona's goal: treat passkeys as a form of identity material, on par with passwords, TOTP, and SSH keys — isolated to the identity domain, per-item key encrypted, auditable, and filled into the browser without the user noticing.

v1 coverage:

- Storage model + full CLI lifecycle (create/list/show/remove, self-test sign/verify)
- Browser extension intercepts WebAuthn registration/authentication flows, signing in core via the bridge protocol
- Interoperability with real sites such as webauthn.io

## 2. Non-Goals (v1)

- **No OS-level passkey provider** (macOS Credential Provider / Windows passkey plugin) — that is Phase 4 and requires a native shell project
- No conditional mediation (the browser autofill UI is invisible to extensions; v1 uses an explicit selection UI)
- No cross-device hybrid transport (caBLE/hybrid): Persona is a local software authenticator and does not need cross-device transport
- No CTAP2 USB/NFC/BLE transport layer: Persona does not act as a hardware key
- No attestation (att fmt = `none`; `packed` self-attestation left as a future option)
- No promise of cross-manager passkey export: the FIDO credential exchange protocol (CXF) is not finalized; the design reserves fields but does not implement them yet

## 3. Minimal WebAuthn Knowledge Set (the parts directly tied to the implementation)

A passkey consists of these bytes, all spec-defined and all testable:

| Component          | Description                                                                                         |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| Key pair           | ES256 (ECDSA P-256 + SHA-256), the algorithm mandated by WebAuthn; signatures DER-encoded           |
| `credential_id`    | Globally unique byte string; a software authenticator can use 32 random bytes                       |
| `user_handle`      | User identifier on the RP side (generated by the RP, passed through and stored verbatim at registration) |
| COSE_Key           | COSE/CBOR encoding of the public key (EC2 + P-256 + ES256 → alg -7)                                 |
| authenticator data | `rpIdHash(32) ‖ flags(1) ‖ signCount(4) [+ attestedCredentialData + extensions]`; flags carry UP/UV/AT |
| client data        | The JSON bytes of `{"type":"webauthn.create"/"webauthn.get","challenge":…,"origin":…}`              |
| Registration artifact | attestation object (fmt `none`: `{fmt, attStmt:{}, authData}`) + clientDataJSON                  |
| Assertion artifact | `credentialId + authenticatorData + signature(authenticatorData ‖ SHA256(clientDataJSON))`          |

RP-side validation rules that matter to us:

- `rpIdHash` must equal SHA-256(rp_id)
- The origin's effective domain must match rp_id (or rp_id must be its registrable suffix) — **this is the core anti-phishing check, and core must enforce it**
- signCount: software authenticators almost universally keep it at 0 (1Password and Bitwarden do the same), which means no clone detection — see the threat model

## 4. Overall Architecture and Trust Boundaries

```
浏览器页面                    扩展（不持任何密钥）                core / persona bridge
┌─────────────┐   main-world 拦截   ┌──────────────┐  Native Messaging  ┌─────────────────────┐
│ navigator.  │ ──────────────────▶ │ content/     │ ─────────────────▶ │ 校验 origin↔rp_id   │
│ credentials │   请求参数+origin    │ background   │  配对+HMAC+gesture │ 解锁态签名（ES256）  │
└─────────────┘ ◀────────────────── └──────────────┘ ◀───────────────── │ per-item key 解封    │
   attestation/                     选择 UI                               │ 审计 + 计数          │
   assertion 返回页面                                                      └─────────────────────┘
```

Key decision: **private keys exist only in core process memory (unlocked state); the extension only ever carries request parameters and signature results**. This differs from the existing `request_fill` (where the extension receives the fill value) — for passkeys, not even a sensitive value reaches the extension, only non-sensitive public key artifacts.

The trust boundaries follow `BRIDGE_PROTOCOL.md`: pairing + HMAC + short-lived sessions + origin binding + user gesture; a new core-side origin↔rp_id check is added as the last line of defense (a compromised extension still cannot sign for the wrong domain).

## 5. Data Model and Storage

A new first-class model `PasskeyItem` (at the same level as `Credential`, isolated to the identity domain, using the existing per-item key wrapping hierarchy):

```rust
pub struct PasskeyItem {
    pub id: Uuid,
    pub identity_id: Uuid,          // 身份域
    pub rp_id: String,              // "github.com"
    pub rp_name: Option<String>,    // 注册时 RP 可读名
    pub user_handle: Vec<u8>,       // RP 生成，原样存储
    pub user_name: Option<String>,  // 登录名（展示用）
    pub user_display_name: Option<String>,
    pub credential_id: Vec<u8>,     // 32 字节随机
    pub encrypted_private_key: Vec<u8>, // P-256 标量（32B）密文，item key 加密
    pub wrapped_item_key: Vec<u8>,  // 主密钥包裹的 item key（解开上行密文）
    pub public_key_cose: Vec<u8>,   // COSE_Key 原始字节（展示/导出/自检）
    pub alg: i64,                   // -7 (ES256)；v1 唯一
    pub sign_count: u32,            // 恒 0（软件验证器惯例）
    pub uv_initialized: bool,       // 创建时是否做过 UV
    pub export_allowed: bool,       // 默认 true；false 则导出/备份跳过并告警
    pub created_at: DateTime<Utc>,
    pub last_used_at: Option<DateTime<Utc>>,
    pub tags: Vec<String>,
}
```

- On disk: the `encrypted_private_key` (AES-256-GCM ciphertext encrypted under the item key) and `wrapped_item_key` (the item key wrapped by the master key) fields — fully consistent with `KEY_HIERARCHY.md`, no new encryption path needed; sensitive fields such as `user_handle` go through the same payload encryption
- A unique index on `credential_id` (no duplicates within the same vault; there is no global registry on the RP side)
- The same identity + same rp_id + same user_name may hold multiple entries (the site itself supports multiple passkeys); the selection UI deduplicates for display
- Item history (item versioning): **not implemented** — `EntityType` has no Passkey variant (`change_history.rs`), so passkey rotation/field changes do not enter change_history/item history

`CredentialType` **does not** gain a `Passkey` variant: passkey is a standalone model, to avoid diluting the semantics of `Credential`'s secret fields; the list/search/TUI layers can simply present it as an item type.

## 6. Cryptography and Dependency Selection

Following the principle of "prefer audited libraries":

| Requirement                 | Selection                                                      | Notes                                                         |
| --------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------- |
| P-256 key generation/ECDSA/DER | `p256` (RustCrypto, ecdsa feature)                            | Same family and same maintainer as k256                       |
| COSE/CBOR encoding/decoding | `coset` (maintained by Google, used by Fuchsia, built on ciborium) | Full COSE_Key and COSE_Algorithm constants; no hand-rolled CBOR |
| SHA-256                     | Reuse `sha2`                                                   | rpIdHash, client data hash                                    |

What remains in-house is only the assembly of "authenticator data / attestation object" — a small stretch of spec-fixed byte assembly (~100 lines), with regression testing done against an RP-side library (see §12) — the same strategy as the wallet migration: libraries for protocol codecs, standard vectors as the backstop.

In-memory form of the private key: `p256::SecretKey`; it goes through the `zeroize` path both before and after hitting disk (consistent with existing secret handling).

## 7. Bridge Protocol v2

Three new messages on top of v1 (all require `auth` HMAC + `origin` + `user_gesture`); the `hello` capability list gains `passkey_create`, `passkey_assert`, and `passkey_list`:

### 7.1 passkey_list — List the passkeys for a given RP (data source for the selection UI)

```json
{
  "type": "passkey_list",
  "origin": "https://github.com",
  "payload": { "rp_id": "github.com" }
}
```

After core verifies that rp_id matches the origin, it returns a non-sensitive summary: `[{id, rp_id, user_name, user_display_name, created_at}]`. **No bytes beyond these summary fields are returned** (never private key material).

### 7.2 passkey_create — Registration (attestation)

```json
{
  "type": "passkey_create",
  "origin": "https://github.com",
  "user_gesture": true,
  "payload": {
    "request_json": {
      /* PublicKeyCredentialCreationOptions 的 JSON 形态 */
    },
    "client_data_json_b64": "…", // 浏览器产出的原始字节，core 只做哈希，不重组
    "require_resident_key": true
  }
}
```

Core-side flow:

1. Parse options: take `rp.id` (defaulting to the origin's effective domain), `user.id` (user_handle), `user.name`, `pubKeyCredParams` (accept only ES256; refuse if absent)
2. **`origin` validation**: the `origin` inside `client_data_json` must match the request `origin`, and the effective domain must satisfy the registrable-suffix relationship with rp_id
3. **`challenge` does not participate in semantic parsing**: only base64url format validation (`URL_SAFE_NO_PAD` decode check); the content is not interpreted, is kept as-is inside client_data_json, and SHA-256 is taken only over the complete bytes
4. Generate key pair + credential_id (random 32B) → assemble authenticator data (rpIdHash, UP|UV|AT, signCount=0, AAGUID, credential_id, COSE public key) → `{fmt:"none", attStmt:{}, authData}`
5. Persist the `PasskeyItem` — **passes only the unlock gate (`create_passkey_full` only calls `ensure_unlocked`), not the sensitive-operation re-auth/biometric gate** (that gate is only wired to the assertion/self-test/export paths); the bridge path additionally has desktop approval for a second consent (`desktop_approval_gate`), then returns the attestation response

### 7.3 passkey_assert — Authentication (assertion)

```json
{
  "type": "passkey_assert",
  "origin": "https://github.com",
  "user_gesture": true,
  "payload": {
    "item_id": "uuid", // 用户在 UI 选中后传入；缺省时 core 拒绝（不允许静默选钥）
    "client_data_json_b64": "…"
  }
}
```

Core-side flow: the same origin↔rp_id validation as 7.3 → assemble `authenticator_data` (UP|UV, signCount=0, no AT) → `signature = ES256_sign(priv, auth_data ‖ SHA256(client_data_json))` (DER; the signature input order follows WebAuthn spec §6.5.6: authenticatorData first, clientDataHash after) → return `{credential_id_b64, authenticator_data_b64, signature_der_b64}` → audit `passkey_asserted{rp_id, origin, item_id, result}`.

### 7.4 Version Compatibility

Bump `protocol_version` to 2; a v1 extension receiving an unknown message returns the existing `unknown_type` error code — backward compatible. The protocol doc gains three sections plus error codes: `passkey_rp_mismatch`, `passkey_alg_unsupported`, `passkey_item_not_found`. (An earlier draft listed `passkey_origin_mismatch` — the code never produces that error code; origin↔rp_id mismatch uniformly goes through `passkey_rp_mismatch`.)

## 8. Browser Extension Integration

### 8.1 Interception Method (same approach as Bitwarden; verified feasible on Chromium)

- A content script injected with `world: "MAIN"` (supported by MV3) replaces `navigator.credentials.create/get` with a small shim: it first captures page parameters and the calling-stack origin, then forwards them to background, which aggregates `user_gesture` (read `navigator.userActivation.isActive` synchronously at injection time)
- The replacement keeps a reference to the original function: when no passkey matches or the user cancels, it **falls back to calling the native implementation** — it never blocks the site's native flow
- Conditional mediation (`mediation: "conditional"`) requests are not intercepted in v1 and fall straight back to native

### 8.2 Selection UI

- `passkey_create`: a confirmation dialog shows "Create a passkey for <rp_id> (<origin>), account <user_name>"; the bridge request is sent only after confirmation
- `passkey_assert`: `passkey_list` pulls the candidates → the dialog lists them (user name + creation time + identity name) → the user clicks to select → `passkey_assert`. **No dialog and no request when there are no candidates**; even a single candidate requires an explicit click (1Password behavior, to prevent silent signing)
- The dialog UI reuses the extension's existing popup/confirmation styling; domains are displayed with the full origin, and scenarios where rp_id differs from origin (a legitimate subdomain) carry an explanatory note

### 8.3 Platform Limitations (to be written into user documentation)

Safari does not support main-world injection to intercept WebAuthn — passkeys under the Safari host shell depend on the Phase 4 OS provider. Chromium (Chrome/Edge/Brave) is fully covered in v1.

## 9. Security Design

- **origin↔rp_id validation is enforced in core** (§7.2); extension-side validation is only a UX pre-check — this is the last line of defense once the extension is compromised
- **UV flag mapping**: **passed straight through, not wired to local authentication** (recorded faithfully: this is the intended design and not yet implemented) — the extension sets `user_verification` based on `publicKey.userVerification !== 'discouraged'` (`webauthnHook.ts` → bridge → `core`, where `true` sets FLAG_UV); an RP requiring UV does not first trigger the master-password re-auth/biometric gate. The UV bit currently reflects only the RP's preference declaration and does not prove that this operation passed local user authentication
- **user presence (UP)**: guaranteed by the user gesture; bridge requests missing `user_gesture: true` are refused outright
- **No silent signing**: no assert without a selection UI click; the audit log can distinguish "user-selected" from "automatic"
- **AAGUID**: a fixed, Persona-specific readable ASCII constant `"PersonaPasskey01"` (16 bytes hardcoded in `models/passkey.rs`, not a randomly generated UUID pinned afterward), so an RP can recognize Persona without an attestation assertion
- **challenge/counter**: the challenge gets only base64url format validation, with its content never parsed; signCount is always 0, and item details tell the user that "software passkeys have no clone detection"
- **Audit**: the three events `passkey_created` / `passkey_asserted` / `passkey_exported` carry item_id/identity_id and a success flag; the only metadata key is `via` (`extension`|`os_provider`, asserted only) — **rp_id, origin, and client_data digests go only into tracing logs, not into audit events** (challenge plaintext and signatures are not recorded)
- **Export**: `export_allowed=false` **takes effect only on JSON/YAML export commands** — the private key is skipped and a warning is printed (`cli/src/commands/export.rs`); **encrypted backups do not check this flag** (VACUUM INTO is a physical-snapshot semantic, so passkey private keys go into the backup with the vault) — a known boundary, recorded faithfully. The default is true (consistent with 1Password: passkeys must be migratable with the vault)

## 10. Threat Model Additions (merged into THREAT_MODEL.md)

| Threat                                                   | Controls                                                                                                                                          |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| A phishing site initiates an assertion with a legitimate rp_id (malicious page on the same domain) | The selection UI shows the full origin + an explicit user click; the audit trail records it; same same-origin policy as password fill |
| Extension is compromised and requests signatures for arbitrary domains | Core-side origin↔rp_id check + HMAC pairing bound to the extension instance + user gesture + desktop confirmation policy (same tier as `confirm_on_fill`) |
| A page triggers WebAuthn from a hidden iframe            | The interception layer rejects cross-origin iframe contexts (the WebAuthn spec itself forbids it; the interception layer is a second line of defense) |
| Unlocked-state automation scripts borrow the bridge for silent signing | Same approach as the SSH agent: passkey assert goes through the sensitive-operation re-auth/biometric gate and can be enforced by policy |
| An exported backup leaks passkey private keys            | Encrypted at the same tier as the vault (Argon2id backup encryption); `export_allowed=false` only skips the private key on JSON/YAML export — backups are physical snapshots and do not check the flag (known boundary); export events are audited |
| signCount=0 means no clone detection                     | An accepted limitation (the industry norm for software passkeys); stated plainly in item details                                                |

## 11. Import/Export

- Vault export (JSON/YAML): passkey items participate according to the §9 rules; encrypted backups continue to use the Argon2id path
- Import from other managers: the export formats of 1Password and Bitwarden both contain passkey private key fields (1PUX's `truncatedUpdateToken` … they all differ) — **1PUX import does not handle passkey fields (not implemented)**: `import_1pux.rs` has no passkey parsing at all, consistent with the §13 P4 schedule (cross-manager passkey import is a distant-future item)
- Cross-manager standard exchange (CXF): the `foreign_key_ref` field is planned as a reservation — **planned, the field has not landed** (the `PasskeyItem` model and storage do not contain that field), to be implemented once FIDO finalizes the standard

## 12. Testing and Interoperability Verification

- **Unit/spec vectors**: COSE_Key encoding, authenticator data byte layout, `none` attestation object, DER signatures, rpIdHash, and the registrable-suffix matching table (including the `github.com` vs `www.github.com` vs `evil-github.com` counterexamples)
- **RP-side regression**: bring in `webauthn-rs` as a dev-dependency (a mature relying party implementation) and run core artifacts through full RP validation (attestation verify + assertion verify) — the same philosophy as the wallet's official-vector backstop: our authenticator-side code is small, so we use the other side's implementation as the referee
- **Bridge protocol**: positive and negative cases for the three new messages (missing origin / missing gesture / rp mismatch / unpaired / unsupported algorithm)
- **Fuzzing**: `client_data_json` and options JSON parsing added to the fuzz list (malformed `webauthn.create` inputs)
- **Manual interoperability**: webauthn.io (registration + login), webauthn.bin.coffee, and GitHub passkey login; go through each once on Chromium and Edge
- **Audit spot checks**: per the THREAT_MODEL quarterly process, verify that no plaintext challenge or signature ends up in logs

## 13.1 P4 Implementation Plan (OS passkey provider + conditional mediation, refined 2026-09-22)

The two P4 items are **the same workflow**: the browser's conditional-UI dropdown is invisible to extensions
(§2, §8.1), and the only way for Persona items to appear in the native passkey selection UI is to register a
credential provider with the OS. Intercepting `mediation: "conditional"` on the JS side and fabricating our own UI would break the native passkey fallback — explicitly not done.

Prerequisites: real macOS/Windows machines and a signing environment (this repo's Linux CI only does protocol and core regression).

| Step | Platform | Contents                                                                                                                                                                                                                                | Acceptance                                                                        |
| ---- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| P4.1 | Common   | Already landed (2026-09-24, protocol v3): the `passkey_credential_provider_list/assert` message family (`docs/BRIDGE_PROTOCOL.md` §12/§13), reusing HMAC pairing and the user gesture gate; the core-side origin↔rp_id check is unchanged                                            | Protocol cases (cli bridge 46 tests) + desktop approval whitelist cases pass     |
| P4.2 | macOS    | AuthenticationServices `ASAuthorizationCredentialProviderExtension` + `ASAuthorizationPlatformPublicKeyCredentialProvider`: the system shows "Sign in with Persona" → the extension process calls the persona bridge via App Group/Unix socket → provider assert | Persona items appear in the conditional-UI dropdown of Safari/Chrome; webauthn.io login works |
| P4.3 | Windows  | Windows Hello passkey plugin (WebAuthn UX entitlement / Credential Provider): the system selector surfaces Persona items → local IPC calls the bridge                                                                                    | Persona items appear in conditional-UI on Edge/Chrome; GitHub login works        |
| P4.4 | Common   | Already landed (2026-09-24, with P4.1): the provider path's assert goes through exactly the same sensitive-operation gate and desktop approval gate as the extension; the `passkey_asserted` audit carries `via=extension\|os_provider` metadata (`log_audit_with_metadata`), so provider-originated events can be traced independently             | Protocol/audit cases green                                                      |

## 14. Open Questions

1. **Multiple identities hitting the same rp_id**: should the selection UI filter by active identity before listing (aligned with the password suggestion's "active identity first" policy)? Tendency: filter to the active identity by default, with a "show other identities" expansion
2. **Private key backup format**: custom JSON for export (v1), or also provide a PKCS#12-style standard container? (No standard exists until CXF is finalized; v1 custom + documented schema)
3. **Re-evaluate after P3** whether `confirm_on_passkey_assert` should become a standalone policy key (currently it reuses `confirm_on_fill`)
